# 直接解题与工作台的配对试验

A 直接解题，B 使用 Modeling Workbench 0.8 托管流程。两组各由一个 Terra medium 会话开发，B 的独立复核也使用同模型的新会话。每项对照定稿后生成三批新棋盘，每批四张图各 20 局。下面的过线批数按原裁判统计。标准赛道的三张图必须同时满足挑战条件。

| 试验与提交 | 标准过线批数 A / B | 湿地过线批数 A / B | 观察 |
|---|---:|---:|---|
| 第一对会话初稿 | 0 / 3 | 0 / 0 | 标准赛道两组均通关 180/180，果园成本达标分别为 22/60、34/60 |
| 同一对会话接受反馈后 | 1 / 3 | 0 / 2 | 在本轮 60 张湿地图上，B 改前、改后成本达标从 6 提升到 28；A 从 0 提升到 11 |
| 第二对会话，约 1 万输出 token | 0 / 2 | 0 / 0 | A 用 10,021，B 用 9,985 |
| 第二对会话，约 2 万输出 token（同期） | 2 / 2 | 2 / 0 | A 用 21,115，B 用 20,595；湿地达标分别为 32/60、18/60 |
| 第二对会话，最终提交 | 3 / 2 | 2 / 0 | A 用 32,659，B 含复核用 41,733；均通关 239/240，总成本达标分别为 196、180 局 |

初稿与返工评测使用不同的新棋盘。判断返工收益时，要在返工轮的棋盘上重跑旧程序。以 A 的果园为例，同图达标从 27/60 提高到 43/60，却新增两局提前停止。成本和通关都影响整批验收。

第二对会话的预算按累计输出（含推理）计，输入及缓存输入不计入预算。约 2 万档在表中选取用量相差 520 的同期版本。按预先公布的 5% 上浮规则选择最近提交，则是 A 的 15,362 对 B 的 20,595，标准过线 0 / 2、湿地 1 / 0。最终行记录自然结束时的实际用量。B 从 20,595 到最终交付的程序字节相同，其间复核确认了湿地成本未过线，新增候选在开发对照中更差，因而保留原程序。B 的内部验收仍有未解决项。

**解释范围。** 两对开发会话给出了不同的赛道结果。相同棋盘让两份程序的成本差可以逐局核对；换了随机棋盘并没有增加独立开发会话数。这里不能估计整个工作流的通常胜率，也不能从总分分离出复核、更多试算或开发者选择的单独作用。

## 在本目录重放

```sh
python3 replay.py budget paired20 --batch 1 --suite boss
```

该命令用历史种子运行两份定稿程序，核对原始逐局记录的 SHA-256，再调用原裁判打印两组的相对名次及判据。核对包含棋盘编号、终止原因、成本和达标字段，排除随机器变化的耗时。发布的种子用于复现；新比赛请在定稿后另抽种子。每局超时为 10 秒。

| 试验 | 提交对 | 选取方式 |
|---|---|---|
| `fresh-study` | `final` | 第一对会话初稿 |
| `feedback` | `before`、`after` | 第一对会话返工前后，在相同的返工评测棋盘上分别比较 A、B |
| `budget` | `10000`、`20000`、`paired20`、`final` | 第二对会话的约 1 万、公式 2 万、同期约 2 万和最终提交 |

批次可选 1、2、3，赛道可选 `standard`、`boss`。在 [results.json](results.json) 中，每个试验的 `boards` 是三批种子的十六进制编码，`pairs` 指向 [players/](players/) 中按程序内容去重的文件，`runs` 保存每批每图的成绩和逐局摘要。原始试验对标准、湿地分开评分。
